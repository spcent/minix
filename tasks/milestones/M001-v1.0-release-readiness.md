# M001 MiniX v1.0 Release Readiness

## Summary

This milestone defines the integrated work needed to move MiniX from a `v0.1` architecture proof plus richer novel sample apps into a publishable `v1.0` release. The milestone prioritizes release boundary clarity, real environment wiring, auth and session reliability, unified route protection, platform adapter parity, release-grade verification, and alignment between shared kernel capabilities and the official host samples.

## Goal

Ship a defensible `v1.0` that is usable by humans and safe for agents to extend: the supported product surface is explicit, the runtime is not accidentally mock-backed, auth and request behavior is predictable across H5 and WeChat, host wiring remains manifest-driven, and the repo has enough verification and documentation to support release and follow-up iterations.

The frozen official `v1.0` sample surface includes:

- `apps/host-h5`
- `apps/host-wechat`
- `apps/novel-h5`
- `apps/novel-wechat`

## Non-goals

- adding new platform targets such as Douyin or Alipay
- broadening the main host flow beyond the existing top-level route sets unless release scope is explicitly changed
- introducing a shared cross-platform rendering DSL
- implementing analytics backends, payments, or billing systems
- turning every novel-specific capability into shared core surface in this milestone when a narrower host-level freeze is sufficient

## Scope

- In scope:
  - freeze the `v1.0` release promise and official support surface
  - replace accidental mock-first release behavior with explicit environment selection
  - harden auth, session expiry, logout, and protected-route handling
  - align H5 and WeChat adapter behavior where the runtime contract already implies parity
  - upgrade the main `host-*` apps from demo-grade copy and feedback into usable official samples
  - add release-grade verification beyond static guards and unit tests
  - update docs and versioning guidance to match the actual `v1.0` support story
  - define RC naming, final tag naming, and release-note source of truth
  - identify which novel-app capabilities must become formal shared interfaces before release
- Out of scope:
  - new top-level packages without a boundary reason
  - new route families for the main `host-*` apps
  - remote experimentation infrastructure
  - collaborative or social product features
  - deep performance work unless required to unblock release readiness

## Route Impact

- affected routes:
  - main host routes: `auth.login`, `overview.index`, `items.list`, `settings.index`
  - novel routes used to validate richer release samples: `home.index`, `catalog.index`, `novel.detail`, `toc.index`, `reader.chapter`, `bookshelf.index`, `membership.center`
- new route params:
  - protected-route redirect params may be normalized around `from`, `reason`, and any session-recovery or return-target keys that survive both hosts
  - if auth refresh or recovery introduces new route semantics, those params must be frozen before slice work starts
- removed route params:
  - remove ad hoc or host-only redirect params if they duplicate shared route-guard semantics
- host manifest impact:
  - `apps/*/src/manifest/page-definitions.ts` remains the source of truth
  - generated manifest outputs and WeChat shells will need regeneration after any route or controller option changes

## Contract Impact

- changed shared contract types:
  - auth contract may need a frozen token lifecycle story for `accessToken`, `refreshToken`, `expiresAt`, and any refresh endpoint behavior
  - request and error semantics may need stricter documented treatment for `401`, `403`, timeout, and retriable failures
  - environment and release config shape may need explicit host-facing typing if runtime selection moves out of hardcoded bootstrap code
- changed controller options:
  - auth, items, and settings controllers may shift from page-owned auth redirection into shared route-guard conventions
  - settings controller options may need a narrowed release-facing surface if reader-center controls are not officially supported in the main hosts
- changed store shape:
  - auth and items stores may need additional state for recovery, expired-session feedback, and release-grade error display
  - settings store may need clearer split between demo text-only sections and persisted controls
- changed action names:
  - avoid changing host entry action names unless required by frozen controller interfaces
  - if renamed, update host manifests and generated registries in one integration pass

Shared interface changes are expected in auth, request behavior, and release configuration. They should be kept narrow and frozen before task decomposition.

## Interface Freeze

Freeze these before task decomposition:

- contracts:
  - final `v1.0` auth/session lifecycle contract
  - final protected-request error semantics
  - final supported environment selection contract for host bootstraps
- feature store shape:
  - auth page recovery and redirect state
  - items page persisted progress and unauthorized handling state
  - settings page persisted controls that are officially supported in `v1.0`
- controller actions:
  - auth login, ensure-login, logout, and redirect continuation actions
  - items load, refresh, unauthorized redirect, and progress persistence actions
  - settings ensure-authenticated, persisted control update, and logout actions
- route ids / route params:
  - supported protected-route redirect params
  - supported return params for reader/settings or auth recovery flows
- storage keys:
  - session storage key
  - items progress storage key
  - reader display and reading-center storage keys if kept in release scope
- generated outputs impacted:
  - `apps/*/src/manifest/app.manifest.ts`
  - `apps/*/src/manifest/page-manifest.ts`
  - `apps/*/src/manifest/page-config.ts`
  - `apps/*/src/registrations/page-registry.ts`
  - `apps/*/miniprogram/pages/*`

## Execution Plan

### Critical Path

- freeze `v1.0` release scope, official app/host support matrix, and non-goals
- freeze auth, request, environment, and route-guard interface changes
- implement runtime and adapter changes needed for real environment selection and auth/session reliability
- align main `host-*` apps with the frozen release-facing capability set
- add release-grade verification gates and update documentation to match shipped behavior
- regenerate derived outputs and run final repo verification

### Integrator Responsibilities

- confirm the frozen `v1.0` support surface before parallel slice merge
- update host source manifests where controller option or route-contract changes require it

- ensure the final release commit keeps the coordinated `1.0.0` package manifests and runtime version stamps before the `v1.0.0` tag is created

## Verification Plan

### Slice Gates

- `pnpm verify:feature auth`
- `pnpm verify:feature items`
- `pnpm verify:feature settings`
- targeted tests:
  - auth session restore, expiry, logout, and redirect continuation
  - request unauthorized, forbidden, timeout, and retryable failure mapping
  - platform adapter contract tests for H5 and WeChat parity
  - host bootstrap tests proving mock vs non-mock environment selection
  - settings persistence and items progress persistence tests

### Integration Gates

- `pnpm gen:manifests`
- `pnpm gen:shells`
- targeted host checks for `host-h5`, `host-wechat`, `novel-h5`, and `novel-wechat`
- release smoke flow covering the official main host loop on both H5 and WeChat

### Final Gate

- `pnpm verify`

### Manual Review Path

- release runbook:
  - `docs/RELEASE_RUNBOOK.md`
- route flow to click through:
  - H5 main host: `login -> overview -> items -> settings -> logout`
  - WeChat main host: `login -> overview -> items -> settings -> logout`
  - novel sample spot-check: `login -> catalog/detail -> reader or membership -> return`
- state transitions to confirm:
  - unauthenticated access into protected routes
  - expired session recovery path
  - logout clearing local session and returning to login
  - persisted items progress and settings state surviving navigation and restart
  - environment selection using the intended adapter instead of accidentally falling back to mock
- regressions to watch:
  - host manifest drift
  - generated shell drift
  - H5/WeChat adapter behavior divergence
  - novel sample capabilities silently depending on unfrozen main-host contracts

## Risks / Follow-ups

- risk:
  the repo currently mixes a narrow main host proof path with richer novel samples, which can cause `v1.0` scope creep during implementation
- risk:
  auth refresh semantics may widen contracts more than intended if the release decision is not made early
- risk:
  adapter parity work can expose host assumptions hidden in H5 no-op UI or mock-only flows
- risk:
  generated host outputs will drift if controller or route changes merge before integrator regeneration
- follow-up:
  if novel entitlement, reader continuity, or bookshelf coordination stabilizes during this milestone, capture the next extraction work as a separate post-`v1.0` milestone instead of widening this one late
- follow-up:
  if CI or release automation cannot be fully landed in this milestone, define a minimum required release checklist and make the gap explicit before tagging `v1.0`
